# Localization

ShitSpeak localizes two kinds of text for each client:

- **Server text**: login rejections, permission denials, notices and context
  menu labels generated by the server. These live in this repository under
  `translations/server/` and are translated in Weblate.
- **Channel names**: user content. Each raw channel name is used as the
  translation key in a separate Weblate component, and every client sees the
  names in its own language.

A client's language is resolved from `force_language`, then the language the
authenticator returns, then `default_language` (see
[Configuration](configuration.md#localization)). The language is a BCP-47 tag
matched against whatever languages exist at the moment, so `es-MX` is served
by a Spanish catalog and `zh-CN` by `zh_Hans`, and languages that translators
add in Weblate are used without a server release.

## Server text

### Files

`translations/server/<code>.json` holds one language per file, named with the
Weblate language code (`en.json`, `pt_BR.json`, `zh_Hans.json`). Each file is
a nested JSON object:

```json
{
  "reject": { "WrongUserPw": "Incorrect username or password" },
  "text": { "ChannelDoesNotExist": "Channel {channel_id} does not exist" }
}
```

`en.json` is the source catalog. It must define every key the server uses; the
tests fail otherwise, and they also reject keys that nothing uses. Other files
may be partial: a missing or empty string falls back to English for that one
string.

Placeholders are written `{name}`. A translation must use exactly the same
placeholders as the English source; an entry that doesn't is ignored (with a
warning) and English is used for it.

Every file in the directory is compiled into the binary, so a language that
Weblate commits is shipped with the next build without any code change.

Adding a message:

1. Add a variant to `TextKey` in `crates/shitspeak-runtime/src/localization/mod.rs`.
2. Add the English text under `text` in `translations/server/en.json`.
3. Use it through the client (`sender.text(TextKey::…)` or
   `sender.format_text(TextKey::…, &[("name", value)])`), so it is rendered
   in that client's language.

Translators then pick the new string up in Weblate.

### Connecting the repository to Weblate

Create a component for the repository with these settings:

| Setting | Value |
|---|---|
| File format | JSON file |
| File mask | `translations/server/*.json` |
| Monolingual base language file | `translations/server/en.json` |
| Template for new translations | `translations/server/en.json` |
| Source language | English |
| Language code style | Weblate default (`pt_BR`, `zh_Hans`) or BCP style; both are accepted |
| Translation flags | `python-brace-format` (enables Weblate's placeholder check for `{name}`) |

Weblate then commits translations back to `translations/server/`.

### Live updates

A running server can also fetch translations from the same component directly,
so a translation saved in Weblate reaches users without waiting for a
commit, build and deploy:

```toml
[translation_sync]
url = "https://weblate.example.org"
project = "shitspeak"
component = "server"
# token = "wlu_..."          # needed only for private projects
poll_interval_secs = 300
cache_path = "data/localization/server.json"
```

Every poll lists the component's languages and downloads only those whose
last change differs from the previous poll. Live strings are layered over the
bundled catalogs. A string that Weblate does not provide keeps its bundled
text, and a string that fails the placeholder check is ignored. Strings marked
"needs editing" in Weblate are never served. A new language that appears in
Weblate is served straight away.

Server text is rendered when it is sent, so an update affects the next message
generated. `cache_path` keeps the last download so a restart serves the same
translations while Weblate is unreachable.

## Channel names

Channel names are not in any language, so the raw name is the translation key.
The server keeps a Weblate component in sync with the channel tree:

1. **Push**: channel names Weblate doesn't know yet, root names included, are
   added as source strings. Up to 200 names are pushed per poll, and the rest
   follow on later polls.
2. **Fetch**: translated strings are downloaded for every language whose last
   change moved.
3. **Present**: every `ChannelState` sent to a client has its name replaced
   with the translation for the client's language. That covers the initial
   channel tree, renames, the root channel, and web gateway clients.
   Untranslated names are sent as entered.
4. **Update live**: when a translation changes, connected clients whose
   language is affected get the new name for every affected channel they can
   see. Channels hidden from a client are never sent to it.

The server keeps storing and comparing the raw names. Duplicate-name checks and
renames operate on them.

### Editing a translated channel

Mumble's Edit Channel dialog fills its name field from the name the client
currently shows, at the moment the server answers the dialog's ACL query. So
the server wraps that answer: a `ChannelState` with the raw name (sent
untranslated), then the ACL reply, then the translated name again. The dialog
therefore shows and edits the raw name while the channel tree keeps the
translation.

When the dialog is saved without touching the name, the client sends the raw
name back. The server ignores a name equal to the current one, so this is not a
rename; for the root channel it no longer produces "Cannot rename the root
channel".

A rename or translation update can reach the client while that reply is being
queued. To cover that, the server reads the name again after queueing:

- If the raw name changed, it re-sends the reply and Mumble reopens the dialog
  with the current name.
- If only the displayed name changed, it re-sends the current translation.

As in stock Mumble, an open dialog doesn't follow renames made after it opened.

### Setting up the Weblate component

The component may live on a different Weblate instance or project than server
text.

1. **Create a custom language for the keys.** Raw names aren't in any real
   language, so in Weblate's admin interface (*Languages → Add language*)
   create one, for example code `x_channel`, named "Channel name (key)". Give
   it a single plural form.
2. **Create the component** with:
   - format "JSON file"
   - monolingual base file `channel-names/x_channel.json`
   - source language `x_channel`
   - file mask `channel-names/*.json`

   It can live in its own repository, or in a "local" Weblate repository with
   no upstream. The server never reads the files, only the API.
3. **Enable "Manage strings"** on the component, so strings can be added
   through the API.
4. **Create an API token** that can add strings to the component: a project
   token, or a user token for a user with the *Manage strings* permission.
5. **Add target languages** for translators as usual.

The server finds the source language itself: it's the language Weblate marks
as the component's source.

```toml
[channel_name_translation]
url = "https://names.weblate.example.org"
project = "community"
component = "channel-names"
token = "wlu_..."
poll_interval_secs = 60
push_names = true
cache_path = "data/localization/channel_names.json"
```

Set `push_names = false` if the source strings are maintained by other means.
In that case a read-only token (or none, for public projects) is enough.

### Caveats

- Opening the Edit Channel dialog briefly renames the channel to its raw name
  and back in that client's tree, which client plugins see as two "channel
  renamed" events.
- `mumble://host/Channel/Sub` links resolve channel paths against the names the
  client displays, so such links are language-specific.
- Channel names removed from the tree are not deleted from Weblate.

## Language changes

Reauthentication can return a different language. When it does, text the
server generates from then on uses the new language. The server also re-sends
the name of every channel the client can see, which reverts names with no
translation in the new language, and refreshes the server context-menu labels.
The same happens for web gateway clients.

## Reloading configuration

`[translation_sync]` and `[channel_name_translation]` are read on every poll,
so changes apply without a restart:

- Enabling a section starts polling within 30 seconds.
- Changing the URL, project or component starts over with the new component.
- Disabling a section stops polling and falls back to the bundled catalogs, or
  to raw channel names.

A cache file is only used for the component it was downloaded from.

Tokens can be supplied through the environment instead of the file, for
example `SHITSPEAK_CHANNEL_NAME_TRANSLATION__TOKEN`.
