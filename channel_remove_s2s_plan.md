# ChannelRemove S2S Safety — Design Plan

## Problem Statement

Before a `ChannelRemove` message is delivered to any Mumble client, every `UserState{channel=parent}`
for every client formerly in that channel must already have been delivered on the same TCP socket.
Violation crashes the Mumble client.

In single-node mode this is trivially satisfied: `handle_channel_remove` moves all locally-owned
clients synchronously before calling `delete_channel`, and the per-client socket serialiser is FIFO.

In S2S mode two independent replication topics exist — strict (channels) and owner-scoped (clients)
— and no cross-topic causal ordering is guaranteed. The strict `DeleteChannel` op can arrive at a
node before the owner-scoped `UserState{channel=parent}` moves for remote clients, causing the crash.

A `client_version_dep` field on `DeleteChannel` does not work because:
1. The originating node cannot know what version the remote owner will assign to the resulting
   `UpdateGlobalState` entry — that version is determined at apply-time on the owner, in the future.
2. If a node restarts, its client-log version resets to zero; a version-dep recorded in a committed
   strict op (which lives in the WAL forever) can never be satisfied on the new instance, deadlocking
   the delivery pipeline.

---

## Solution — Two-Phase Strict Channel Op

Leverage the existing strict-replication total-order guarantee. Encode both phases as consecutive
entries in the same strict channel topic, so every node is guaranteed to process Phase 1 before
Phase 2 with no interleaving.

Each two-phase sequence is identified by a **nonce** (UUID or random u128 generated by the
originator at request time). The nonce is embedded in Phase 1 (`MarkPendingDelete`), Phase 2
(`DeleteChannel`), and any rollback (`CancelPendingDelete`). This ties the three ops together and
makes stale or racing ops safe to ignore.

### Phase 1 — `ChannelOp::MarkPendingDelete { id: u32, parent_id: u32, expires_at: UnixMs, nonce: u128 }`

Proposed by the originator (the node whose client issued the `ChannelRemove` request).
`parent_id` is the preferred destination for displaced clients (the channel's parent, or root if
none); `expires_at` bounds the hold window before automatic rollback.

The proposer treats the time between `MarkPendingDelete` commit and `DeleteChannel` commit as a
**bounded operation window** (equal to `expires_at − now`). If the proposer has not received its
own `DeleteChannel` commit before the window expires, it stops driving the sequence and yields to
the watchdog rollback mechanism. This prevents a partitioned-then-recovered proposer from re-driving
a deletion after the window has long since expired and been rolled back by other nodes.

**Every node applies this op by:**

1. Walking the full subtree rooted at `id` (using `collect_subtree`, the same helper used by
   `delete_channel`). For each channel in the subtree, set `channel.pending_delete = Some(nonce)`.
   This marks the entire subtree — not just the root — so that any client in a sub-channel is also
   displaced.
2. Blocking new joins to any channel in the subtree (join handler checks `pending_delete.is_some()`
   on the target channel and all ancestors; see edge case B).
3. Scanning the local `ClientRepository` for sessions whose `current_channel_id` is any channel
   in the subtree.
4. For each such session:
   - If **locally owned**: perform an ACL check for `parent_id` from the session's perspective
     (see "ACL and fallback" section below). Call `set_current_channel_id(resolved_dest)` through
     the normal `GlobalStateWriteGuard` path. This produces a real versioned owner-replication
     delta. That delta carries `channel_version_dep = version_of(MarkPendingDelete)` so that remote
     nodes buffer it until they have applied the `MarkPendingDelete` op themselves.
5. Arming a local watchdog timer for `expires_at` to drive rollback (see rollback section).

**What `MarkPendingDelete` does NOT produce on the wire:** No `ChannelState` Mumble message.
The channels remain visible to connected clients until `ChannelRemove` is sent in Phase 2.

### Phase 2 — `ChannelOp::DeleteChannel { id: u32, nonce: u128 }`

Proposed by the originator immediately after Phase 1 commits, provided the proposer's local
channel state still shows `pending_delete == Some(nonce)`. If not (cancel already committed),
abort — no `DeleteChannel` proposal is made. Carries the same `nonce`.

**Every node applies this op by:**

1. Checking that `channel.pending_delete == Some(nonce)` for channel `id`. If the nonce does
   not match (e.g. a `CancelPendingDelete` rolled back Phase 1 and a new sequence started),
   `apply_op_to_map` treats the op as a **no-op** and does not remove the channel. This prevents
   a stale late-arriving `DeleteChannel` from deleting a channel that has been legitimately
   restored and possibly re-populated.

   **The strict replication layer has no semantic awareness of nonces** — it commits all valid
   proposals blindly. The nonce check is application-layer only. `apply_committed_operation`
   calls `apply_op_to_map` (which may silently no-op) and then unconditionally calls
   `self.tx.send(op)`, broadcasting the committed op to every subscribed per-socket delivery task.
   Without a secondary guard in the delivery layer, `op.to_message()` would return
   `ChannelRemove{id}` and the socket would forward it to Mumble clients even though the channel
   was not deleted — crashing them.

   **Delivery-layer guard:** `convert_channel_operation_to_messages` (which already holds a
   `&Arc<ChannelRepository>`) must check post-application channel state for `DeleteChannel` ops.
   Since `apply_op_to_map` completes before `self.tx.send` fires, the channel map already
   reflects reality by the time the delivery task runs:

   ```rust
   ChannelOp::DeleteChannel { id, nonce } => {
       // Channel still present → nonce mismatch → op was a no-op → emit nothing.
       if channels.get_channel(*id).await.is_some() {
           return vec![];
       }
       vec![ChannelRemove { channel_id: *id }.into()]
   }
   ```

   This same post-commit channel-map check is the **proposer's feedback mechanism**: if the
   channel still exists after `DeleteChannel{N}` commits, the nonce was invalidated and the
   proposer returns a failure to the requesting Mumble client rather than reporting success.
2. Capturing `parent_id` from the channel's `pending_delete_parent` field before removal (it was
   set by Phase 1 and is preserved in both the in-memory map and any snapshot).
3. Walking the full subtree (same `collect_subtree` call) to get all channel IDs being removed.
4. For each session in any subtree channel that has NOT yet been moved (stragglers missed by Phase
   1, e.g. due to snapshot recovery): emit synthetic `UserState` and schedule the real
   `set_current_channel_id` exactly as Phase 1 would, using the shadow-state guard. Under normal
   operation this scan finds an empty set; it is defence-in-depth for the snapshot recovery path.
5. Removing all subtree channels from the map.
6. Emitting `ChannelRemove{id}` to every Mumble socket. Because steps 3–5 are synchronous within
   the channel_log_rx delivery arm, TCP write ordering guarantees the synthetic moves precede
   `ChannelRemove` on each socket.

### Phase 1 Rollback — `ChannelOp::CancelPendingDelete { id: u32, nonce: u128 }`

If Phase 2 is never proposed (originator crashes between phases), the subtree is stuck
`pending_delete` indefinitely.

- `MarkPendingDelete` carries `expires_at` (wall clock). Every node independently watches this.
- When `now > expires_at` and `DeleteChannel{nonce}` has not yet been committed, **any** node
  may propose `CancelPendingDelete{id, nonce}`.
- `CancelPendingDelete` clears `pending_delete` on the root and all subtree channels, but **only
  if their `pending_delete` nonce matches**. Channels already restored (by a prior
  `CancelPendingDelete`) are left untouched.
- Multiple nodes may race to propose the rollback. The strict log commits them in sequence; the
  second and further `CancelPendingDelete{nonce}` ops find no channels with matching nonce and
  are no-ops. Three layered mechanisms keep proposal storms rare in practice:

  **Layer 1 — check-before-propose (eliminates post-commit duplicates).**
  Before calling `StrictHandle::propose(CancelPendingDelete{id, nonce})`, each node reads its
  local channel map. If `channel.pending_delete` no longer holds `nonce` (first cancel already
  committed and cleared it, or a new sequence is in progress), the node discards the proposal
  without sending anything to the replication layer.

  **Layer 2 — per-node jitter on the expiry timer.**
  Each node fires its rollback watchdog at `expires_at + jitter_ms`, where
  `jitter_ms = hash(node_id ⊕ nonce) % MAX_CANCEL_JITTER_MS` (e.g. 2 000 ms).
  The fastest node commits; by the time others fire, Layer 1 kills the proposal.

  **Layer 3 — proposer priority (zero jitter).**
  The node that issued `MarkPendingDelete` already holds the nonce and the expiry. It arms its
  watchdog with `jitter_ms = 0` — it fires at exactly `expires_at`. Other nodes add the Layer 2
  jitter. In the common non-crash case a single proposal enters the strict log. Other nodes act
  as fallback only when the proposer is partitioned or has crashed.
- If a `DeleteChannel{nonce=N1}` arrives after `CancelPendingDelete{nonce=N1}` has already
  cleared the state, the nonce check in Phase 2 step 1 rejects it as a no-op.
- If a `DeleteChannel{nonce=N1}` arrives BEFORE `CancelPendingDelete{nonce=N1}`, the channel is
  deleted; the subsequent `CancelPendingDelete{nonce=N1}` finds no matching pending channels and
  is a no-op.

**Multiple concurrent delete requests for the same channel:**
If two actors simultaneously issue `ChannelRemove` for channel X, two `MarkPendingDelete` ops
with distinct nonces are proposed to the strict log. The second one, when committed, finds X
already `pending_delete` with a different nonce — it is a no-op (or advances the expiry if the
originator retries after a `CancelPendingDelete`). Only the first committed nonce drives the
actual deletion.

## ACL Check and Move Destination Fallback

Moving a user from channel X to `parent_id` requires checking whether that user has permission
to be in `parent_id` (specifically `ACLPermissions::Enter` or equivalent).

- If the ACL check passes: move to `parent_id`.
- If the ACL check fails: fall back to the node's configured **default channel**.
- If the default channel also fails ACL: fall back to root (channel 0), which must always
  be reachable.

**ACL check applies only to locally-owned sessions.** The owning node is authoritative: it
performs the ACL check, resolves the fallback chain, and calls `set_current_channel_id(dest)`.
The resulting `UpdateGlobalState{channel=dest}` is replicated to all other nodes.

**Inconsistent default channels across nodes are acceptable.** Different clients displaced from
the same deleted channel may land in different places if their owning nodes have different
`default_channel` configs. This is the correct behaviour: each node is authoritative for its own
sessions, and those decisions do not conflict. Session ownership is fixed to the node where the
client connected; there is no session migration in the current design.

**Synthetic moves on observer nodes** use `parent_id` from the `MarkPendingDelete` op as a
placeholder. The owner's real decision (parent, default, or root) arrives shortly via owner
replication and supersedes the synthetic. The only purpose of the synthetic is to ensure the
socket's view of the session does not say "still in X" when `ChannelRemove{X}` arrives; the
exact placeholder channel does not need to match the final destination.

## Per-Socket Shadow State and the Drag-Back Problem

### The drag-back problem

Client C is in channel X. C voluntarily moves to channel Y. Node A has not yet received the
`UpdateGlobalState{C, channel=Y}` owner-replication delta. Node A then processes
`MarkPendingDelete{X}`, sees C in X (stale view), emits synthetic `UserState{C, channel=parent_X}`.
Later the real `UpdateGlobalState{C, channel=Y}` arrives. The Mumble socket on Node A has seen
C go: X → parent_X (synthetic, wrong) → Y (real, correct). The socket briefly shows C in the
wrong channel.

Worse: if the per-socket `client_log_rx` arm already delivered `UpdateGlobalState{C, channel=Y}`
to the socket BEFORE the `channel_log_rx` arm processes `MarkPendingDelete`, then the socket
would show C in Y, then back in parent_X (synthetic), then in Y again. C's avatar bounces.

### Does `channel_version_dep` prevent this?

Partially, but not fully. `channel_version_dep = version_of(MarkPendingDelete)` on the owner's
`set_current_channel_id` delta causes `ClientRepository::apply_remote_operation` to buffer the
real move in `pending_remote_ops` until the channel version catches up. When the channel repo's
`apply_committed`/`apply_remote_operation` commits the `MarkPendingDelete` op, it calls
`drain_pending_ops` which drains into `apply_op_inner`.

**Critical detail:** `apply_op_inner` updates in-memory state only — it does NOT call
`self.tx.send(broadcast)`. The per-socket `client_log_rx` arm never sees drained ops through
the broadcast channel. The per-socket loop is only notified about remote client ops through
whatever mechanism the owner-replication layer uses to forward ops to the broadcast tx (a path
that is not yet implemented in `ClientRepository::apply_remote_operation`).

Even once that broadcast path is wired up, `channel_version_dep` would guarantee that the real
move's broadcast fires only after `MarkPendingDelete` has been applied to the channel repo — but
the per-socket `select!` loop may still process the `client_log_rx` arm (real move) before or
after the `channel_log_rx` arm (synthetic). Non-deterministic scheduling. So `channel_version_dep`
is necessary but not sufficient to prevent the drag-back at the per-socket delivery level.

### Per-socket shadow state (the correct fix)

Each per-socket `select!` task maintains a local shadow map:

```rust
let mut session_channel_shadow: HashMap<ClientSessionIdentifier, u32> = HashMap::new();
```

This map records the last `channel_id` that was written to this socket for each known session,
as derived from events already delivered through this task's event loop. It is never shared.

**Maintenance:**

- When `client_log_rx` delivers `AddClient{session=C, channel=ch}`: insert `C → ch`.
- When `client_log_rx` delivers `UpdateGlobalState` with a channel_id delta for C: update `C → new_ch`.
- When `client_log_rx` delivers `RemoveClient{session=C}`: remove `C` from the shadow.

**Synthetic emit decision in the `channel_log_rx` arm for `MarkPendingDelete`:**
For each session C that the global `ClientRepository` reports as being in a pending-delete channel:

- If `session_channel_shadow.get(C) == Some(ch)` where `ch` is in the pending-delete subtree:
  emit synthetic `UserState{C, channel=parent_id}` and update shadow `C → parent_id`.
- If `session_channel_shadow.get(C)` is something else (C already shown as moved): skip.
  The real authoritative move will arrive and be correct.
- If `session_channel_shadow` does not contain C (socket has not been told about C yet): skip.
  When C's `AddClient` eventually arrives via `client_log_rx`, edge case B1 handles it.

The shadow state uses the socket's own consistent view rather than the global `ClientRepository`
state, so it is immune to TOCTTOU races between the two event loop arms.

`channel_version_dep` and shadow state are complementary: `channel_version_dep` provides
cluster-level ordering (the owner's real move is buffered until `MarkPendingDelete` is applied
to the remote channel repo), while shadow state provides per-socket delivery ordering (the
synthetic vs. real arrival order on a given socket never produces drag-back regardless of
scheduling).

## Edge Cases

### A. Snapshot recovery — `MarkPendingDelete` absorbed into snapshot

If a node crashes and recovers from a snapshot taken *after* `MarkPendingDelete` committed but
*before* `DeleteChannel`, the snapshot captures `channel.pending_delete = Some(nonce)` but the
WAL replay no longer contains the `MarkPendingDelete` op. The WAL from the snapshot forward
contains `DeleteChannel{nonce}`, which Phase 2 processing handles via the straggler scan.

**Per-socket shadow state is empty after recovery** — the socket has just been (re-)established.
Any client that connects after recovery will receive a full state sync during auth (the normal
replay path), so their shadow is built from scratch. No synthetic injection is needed during
recovery itself; `DeleteChannel` processing handles the straggler scan.

**On startup from snapshot:** scan the channel map for entries with `pending_delete = Some(nonce)`.
For each: arm the rollback watchdog (they are at or past expiry). Log a warning. No client moves
are attempted yet — clients will reconnect and get clean state after `DeleteChannel` is applied.

### B. Client enters a pending-delete channel

Three sub-cases:

**B1 — Delayed `AddClient` arrives with `channel_id` in the pending-delete subtree.**
An owner produced `AddClient{C, channel=X}` before it applied `MarkPendingDelete`. The entry
travels via owner-replication and arrives at a receiving node AFTER that node has processed
Phase 1. When the `client_log_rx` arm delivers the `AddClient`:

- Insert `C → X` in the shadow.
- Immediately check: is X (or an ancestor) currently `pending_delete`? If yes, emit a synthetic
  `UserState{C, channel=parent_id}` inline before returning from the delivery step, and update
  the shadow to `C → parent_id`.
The owner will shortly produce an `UpdateGlobalState{C, channel=resolved_dest}` from its own
Phase 1 `set_current_channel_id` call. That delta arrives and may produce one more `UserState`
update (no-op if same channel, corrective if owner chose a different fallback). The `ChannelRemove`
arrives after both and is safe.

**B2 — New client connects and authenticates with a remembered channel in the pending-delete subtree.**
The TCP handshake is already complete; the connection cannot be refused. The auth/join handler
checks `channel.pending_delete.is_some()` (and checks all ancestors) on the client's target
channel. If the target is in a pending-delete subtree, redirect silently: apply the same ACL
check + fallback logic as Phase 1 locally-owned moves. The `AddClient` is produced with the
resolved destination channel, which is already correct — no downstream special handling needed.
This is identical to the existing "channel not found → fall back to parent" redirect logic.

**B3 — Voluntary channel join to a pending-delete channel (non-connect).**
A client explicitly requests a join via `UserState{channel=X}` where X is pending-delete. The
join handler returns the same redirect as B2: move to `parent_id` (or default, or root) with
ACL check. The `UserState` handler should treat `pending_delete` as a soft rejection similar to
"max_users reached" rather than a hard permission denial.

### C. Voluntary move racing with Phase 1

Client C voluntarily moves from X to Y. The `UpdateGlobalState{C, channel=Y}` travels via
owner-replication with no `channel_version_dep`. Node A processes `MarkPendingDelete{X}`:

- If `UpdateGlobalState{C, channel=Y}` has been delivered to node A's socket BEFORE Phase 1
  fires: shadow shows `C → Y`. Phase 1 scan skips C. No synthetic emitted. Owner does not call
  `set_current_channel_id` for C (C is already in Y, not in X when the owner applies Phase 1).
  `ChannelRemove{X}` arrives safely — socket shows C in Y.

- If `UpdateGlobalState{C, channel=Y}` has NOT been delivered yet: shadow shows `C → X`. Phase 1
  emits synthetic `UserState{C, channel=parent_X}`, updates shadow to `C → parent_X`. Then
  `UpdateGlobalState{C, channel=Y}` arrives and is delivered (shadow → `C → Y`). Then
  `ChannelRemove{X}` — socket shows C in Y. No crash, but C briefly appeared to move to parent_X.
  This is a cosmetic artifact of the race; it cannot be eliminated without blocking Phase 2 on
  global client-state convergence (which reintroduces the version-dep problems).

  Additionally, the owner does NOT produce `set_current_channel_id` for C (C is already in Y
  when the owner applies Phase 1). So there is no authoritative `UpdateGlobalState{channel=parent_X}`
  to "drag C back" from Y. The shadow corrects itself when the real `channel=Y` arrives.

## Changes Required

| Component | Change |
|---|---|
| `channels.rs` — `Channel` struct | Add `pending_delete: Option<PendingDeleteState>` where `PendingDeleteState { nonce: u128, parent_id: u32, expires_at_ms: i64 }` |
| `channel_repository.rs` — `ChannelOp` | Add `MarkPendingDelete { id, parent_id, expires_at_ms, nonce }` and `CancelPendingDelete { id, nonce }`. Extend `DeleteChannel` with `nonce: u128` |
| `channel_repository.rs` — `apply_op_to_map` | `MarkPendingDelete`: walk subtree, set `pending_delete` on each. `CancelPendingDelete`: walk subtree, clear `pending_delete` where nonce matches. `DeleteChannel`: nonce-check before removal |
| `channel_repository.rs` — `ChannelOperation::to_message` | `MarkPendingDelete` and `CancelPendingDelete` return `None`. `DeleteChannel` continues to return `ChannelRemove` unconditionally — the no-op guard lives in the delivery layer, not here, because `to_message` has no channel-map access |
| `channel_handler.rs` — `convert_channel_operation_to_messages` | Receives `ClientRepository` ref; handles `MarkPendingDelete` (shadow-guarded synthetic scan over subtree); handles `DeleteChannel` (same straggler scan as safety net) |
| `server.rs` — per-socket `select!` loop | Add `session_channel_shadow: HashMap<ClientSessionIdentifier, u32>` local to each socket task; maintain on `client_log_rx` delivery; pass to channel_handler. On `AddClient` delivery, additionally check if the session's channel is `pending_delete`; if so, emit synthetic move inline before returning (edge case B1) |
| `client_repository.rs` — `apply_remote_operation` / `drain_pending_ops` | When applying a drained or direct op, also call `self.tx.send(broadcast)` so per-socket `client_log_rx` sees it (currently missing for remote ops) |
| `server.rs` — auth / join handler | ACL check + fallback when target channel has `pending_delete.is_some()`; treat as redirect (B2/B3), not hard denial |
| `client/handlers/channel_remove.rs` | In S2S mode: propose `MarkPendingDelete`, wait for commit, then propose `DeleteChannel{nonce}`. In non-S2S mode: call `mark_pending_delete` then `delete_channel` synchronously (single-node, no strict replication round-trip needed) |
| Watchdog task | On `MarkPendingDelete` commit: arm timer at `expires_at_ms` (proposer node) or `expires_at_ms + hash(node_id ⊕ nonce) % MAX_CANCEL_JITTER_MS` (observer nodes). On startup-from-snapshot scan: arm timer with observer jitter. On fire: check-before-propose (Layer 1 gate); if `pending_delete` still matches nonce, propose `CancelPendingDelete{id, nonce}` |
| Config | No consistency requirement for `default_channel` across nodes; per-node values are accepted. Add `max_cancel_jitter_ms` (default 2 000) and `pending_delete_timeout_ms` (the `expires_at` window; default TBD) as operator tunables |

## Non-Goals

- Leader election for rollback: timestamp + any-node-may-propose is sufficient.
- Waiting for remote owner acknowledgements before Phase 2: strict total-order makes this unnecessary.
- Versioned client deps on `DeleteChannel`: replaced entirely by this two-phase design.
- Eliminating the cosmetic drag-back artifact in the voluntary-move race (edge case C): doing so
  would require blocking Phase 2 on global client-state convergence, reintroducing the
  unanswerable version-dep problem.
